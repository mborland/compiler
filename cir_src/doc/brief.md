We want to support only non-lowered EDG IL for the CIR back end. Lowered EDG IL is C, non-lowered EDG IL is C or C++, and we want to preserve C++ IL for C++ CIR.
The implementation should be capable of working with IL Write/Read non-lowered EDG IL where the CIR back end could be a secondary process consuming the EDG IL write out.
We want to keep compile times fast. We should factor as much as possible into a "CIR library" that we link during build time when using the CIR back end. We want to use a minimal independent shim to bridge between the CIR library and the front end. The explicit goal is to have absolutely as few situations where a front end change requires the CIR back end portion to be rebuilt partially or fully. The vast majority of front end changes should not result in any CIR rebuild and should quickly link across the shim boundary either dynamically or statically.
We should seek to use an optimized CIR library with debug symbols for our debug front end builds; back ends optimization is a complex and expensive process and back end performance is critical to development velocity.
Give the CIR back end library its own configuration header and source directory (cir_src)
The EDG IL Write/Read process is subject to change. We don't like the complex macro traversal system and it is an artifact of the front end's history. You cannot remove the existing IL Write/Read or modify il_def.h, but you can invent a new IL Write/Read. You should actually prefer invention of a new IL Write/Read if you can build a writer in src that can produce output consumed by the CIR library in cir_src . Consider working backwards from what the CIR back end needs and creating a purpose built IL writer that takes the EDG IL and exports the required portions. If there is information that is optionally useful for optimization in the EDG IL prefer to pack it as supplementary information that the CIR back end always supports but may not always receive. Use bit-packing techniques to mark when extra information is present and should be searched for in the file. Prefer obvious and readable traversal logic. Avoid creating traversal routines that are likely to create significant stack pressure, spend some time planning the most likely problematic areas and prefer a manually managed stack on the heap in these situations. Unlike module processing back end processing needs to consume all relevant IL, this present an opportunity where variable sized streamed formats can out perform random access optimized formats like IFC. Take inspiration from the MessagePack specification https://github.com/msgpack/msgpack/blob/master/spec.md to create a  streamable IL Write/Read where the back end can conceptually start processing while the front end is still producing the output. The CIR back end should act on these packed structures directly so that in cases where the IL Writer and IL Reader are in the same process we can iteratively tag-encode a message and flush it to the back end (minimizing memory pressure, despite the introduction of a new translation layer). If a choice needs to be made, prefer speed over compactness, this is not a network optimized protocol. The guideline to not optimize for bandwidth is not permission to plan for encoding strategies that rely on shared address space or ASLR being disabled, the encoded IL output should not rely on pointer addresses from the process encoding the IL. As a stretch goal make entity references with non-internal linkage stables and resolvable around C++ ODR boundaries (effectively making them mangled IDs). Consider using an identifier table that maps integer values for the translation unit to a mangled name and having introductory messages that introduce new ID -> name values.
Focus on standard C++ first, extensions from other compilers like GNU and MSVC should be added in a later pass to minimize the amount of code that must be initially reviewed.
The front end contains a system where it can discard significant portions of the IL and send them to the back end (see memory region documentation and finish_function_body_processing). Investigate leveraging this to allow a function to be dumped from the front end, packed into the new bespoke format, and passed to the back end for optimization ASAP. Success in this goal would be a significant competitive advantage when compiling large software as it would allow us to stream out functions the front end doesn't need (at least in configurations that are focused on back end codegen with CIR). This would significantly lower memory pressure (especially if the CIR IL file is being written to disk for streamed consumption by a later EDG CIR IL -> CIR compilation process). This could also provide an opportunity for the back end to run concurrently to the front end. Do not implement concurrency, but leave room for future work in this area leveraging the streaming technology, unix sockets, io_uring, and parallel threads of execution.
We have multiple BACK_END_IS_X macros, consider refactoring and consolidating these into a BACK_END_TYPE macro that supports an enumeration. rather than adding a new BACK_END_IS_X macro
