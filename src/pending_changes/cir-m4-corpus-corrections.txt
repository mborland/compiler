CIR back end: corrections found by running the C++ corpus

In the CIR back end configuration (BACK_END_TYPE_CIR), and only in it: the size
of a class that was first met incomplete and completed later is no longer
zero in a new expression; virtual functions that differ in the const or
volatile qualification of this have different signatures and a virtual function
that returns a reference is marked; E1[E2] with the integer first evaluates it
before the pointer; a new[] with a run-time count that is not a nothrow
allocation throws std::bad_array_new_length for a negative or overflowing
count; a placement operator delete that the program declares is called when
the initialization of a new expression throws; a variable whose type is a
const or volatile alignment typedef has that alignment; the base class entry
that the front end puts after the members of a designated initializer is
sent as that of the base; and constructs that need destructors that may throw
to destroy more objects (an array element's default argument, a returned
object) are reported as unsupported instead of being miscompiled.  A class
conditional whose value is discarded, ::delete of an object with a virtual
destructor, a reference bound to a temporary array, __builtin_launder and the
pointer-to-member builtins __builtin_is_corresponding_member and
__builtin_is_pointer_interconvertible_with_class on run-time values are
supported too, as are a destroying operator delete (direct, and through the
deleting destructor), the initializers of members of anonymous unions and
structs in a constructor, class values returned through a comma or a
conditional, and destructors that throw while other cleanups run; the
evaluation order of E1[E2] with the integer first changes only for C++.  The
other configurations are not affected.
